# World-database coverage report and plan

**Status:** planning document, no code written.
**Scope:** TrinityCore `master` `world` (TDB 1210.26091) plus `hotfixes`, against the current editor (`ACWorldEdit`, Godot 4.7 / .NET 8).
**Evidence:** every number and table name below was read from the live `world` database on this machine (247 base tables + 3 views) and from the repository at commit `9ca5dfd`. The reproduction commands are in §2.3.

---

## 1. Goal

Make every one of the `world` schema's 247 base tables *reachable* from a world-editing surface — contextual where the data belongs to something you can see (a creature, a GameObject, a spawn, a quest, a zone), a domain workspace where it does not, read-only where editing it is the server's job — and close the 183 untouched tables in a ranked order that reuses two new engines (a condition strip and a generic row-list page) instead of writing dozens of bespoke editors.

---

## 2. Current context

### 2.1 What the editor is

A 3D world viewer/editor. Reads are read-only transactions over `world`; edits are *drafts* of `RowEdit` records that are exported as guarded SQL and only reach the database when applied from Change History. The layers:

| Layer | Folder | Rules |
|---|---|---|
| Descriptors, rules, drafts, SQL | `Foundation/` | plain .NET, no Godot, no `MySqlConnector` |
| Database reads | `Scripts/Data/` (`AzerothCore/`, `TrinityCore/`) | Godot-free; `Ac*` / `Tc*` per dialect |
| UI | `Scripts/Ui/`, `Scripts/Overlays/`, `Scripts/Viewer/` | Godot types allowed |

The edit pipeline is: source read → `RowSet` snapshot → user edits → `RowEdit(Table, Key, Before, After)` in `InteractionDraft` → `SqlExport` (guarded, preflighted, revertible) → `acworld.change_log` → apply.

### 2.2 What exists today (the surface, not the tables)

- **Creature properties window** (`Scripts/Ui/CreatureProperties/`): Template, Stats, Appearance, Gossip, Vendor, Trainer, Quests, Behavior (SmartAI), Speech, Spawns. Sections register in `Scripts/Ui/CreatureProperties/CreatureSectionRegistry.cs` — one class plus one line.
- **GameObject properties window** (`Scripts/Ui/GameObjectProperties/`): Template, Type properties (per-type `Data0..34` catalog), Quests, Spawns, addon.
- **Quest editor** (`Scripts/Ui/Quest/`): the five core quest tables.
- **Behavior panel** (`Scripts/Ui/Behavior/`): `smart_scripts`, `creature_text`, AreaTrigger rule scopes.
- **Spawn inspector** (`Scripts/Ui/Scene/SpawnInspector.cs`): spawn row + addon overrides, respawn, movement, visibility.
- **Overlays**: creatures, GameObjects, graveyards, AreaTriggers, waypoints, teleports.
- **Content browser** (`Scripts/Ui/Scene/ContentBrowser.cs`), **Pending Changes / Change History**.

### 2.3 How the numbers below were produced (re-runnable)

```bash
# 1. the table inventory (247 base tables, 3 views)
mysql -N -e "SELECT TABLE_NAME FROM information_schema.TABLES WHERE TABLE_SCHEMA='world'" > /tmp/tc_tables.txt

# 2. what the editor catalogues as editable
grep -ho 'new("[a-z_0-9]*"' Foundation/TrinityCore/TcTables*.cs | sort -u

# 3. what any code path mentions
grep -rn --include=*.cs "<table_name>" Foundation Scripts Tests
```

The classification is mechanical: **editable** = a `TableSchema` exists in `Foundation/TrinityCore/TcTables*.cs`; **read-only** = named in `Foundation/` or `Scripts/Data/` but no schema; **untouched** = no reference outside docs. Documentation and test-only mentions were excluded, so "untouched" really means no read path and no edit path.

### 2.4 Assumptions

1. `world` is the target; `hotfixes` is already partially wired (broadcast text, display info, items) and `auth`/`characters` are **out of scope** — they are not world data.
2. "Fully editable" means *reachable and editable through a purpose-built surface* (or explicitly read-only with a stated reason), not "a grid exists for every table".
3. Locale tables are generated by translation tooling downstream; the editor should display them, not author them (§4.4).
4. The draft model (`RowEdit` keyed by a `TableSchema.Key[]`) is fixed. Tables whose real primary key is not unique are handled explicitly (§8, Q3).
5. Both dialects must remain first-class, but TrinityCore master is where the gaps are; AzerothCore parity is judged per slice, and "not applicable" is an acceptable answer for TC-only systems.

## 4. Opportunities for simplification and improvement

### 4.1 One condition strip, everywhere (replaces N per-feature condition editors)

`ConditionCatalog` already models 61 TrinityCore condition types, 36 source types and `Describe(...)` sentences, and `conditions` is already a `TableSchema`. Build **one** `ConditionStrip` control + **one** builder dialog, and drop it under every conditionable thing. This is the single largest deduplication available: gossip options, quest links, loot rows, vendor items, phases, graveyards and SmartAI rules all otherwise grow their own condition UI.

### 4.2 One generic row-list engine (replaces per-feature snapshot readers)

Today each area has its own read method on `IDBSource` (`ReadInteractionAsync`, `ReadQuestAsync`, `ReadBehaviorAsync`, `ReadGameObjectTemplateAsync`, …) and its own section class. That is why adding three small creature tables would otherwise cost three reads + three sections.

Introduce `IDBSource.ReadTableRowsAsync(IReadOnlyList<RowQuery>)` and a UI `RowListSection` driven by the existing `ItemListSpec`. Every "one parent, N child rows, fixed columns" page then becomes a ~40-line descriptor. This is DRY at the layer that has been copied most.

### 4.3 One loot model for 13 tables

`creature_loot_template`, `gameobject_loot_template`, `item_loot_template`, `reference_loot_template` and 9 more share the same columns on TrinityCore. Model once (`LootTables.For(owner)`, `LootModel`, `LootRules`), render once.

### 4.4 Locales: overlay, never editors

3.19 M rows across 15 tables. Add one `LocaleRows` reader that overlays a chosen locale onto the base row for display, plus a Settings language picker. Zero new editors, immediate payoff ("show me the German name").

### 4.5 Fold "quest attribute" tables into the pages that already exist

`quest_details` (emotes), `quest_greeting` (greeting + emote), `quest_mail_sender`, `quest_reward_choice_items`, `quest_reward_display_spell` are not new workspaces — they are blocks on the quest/creature page. Same for `creature_questitem`/`creature_quest_currency` (quest item drops and currency rewards belong next to the creature's quest links).

### 4.6 Fix two documented deviations while touching the area

`AcTeleportSource` is reused for TrinityCore (§`open-work.md` → "Teleports from `game_tele`"), and TC graveyard healers reuse `AcGraveyardSource.ReadHealers`. Both become editable in Slice 8; fold them into one shared, editable `game_tele` source then, rather than building on the deviation.

### 4.7 A read-only inspector instead of 36 stub editors

For the no-editor tables, one `DataInspectorWindow` (opened from View menu, `Ctrl+Shift+D`) that takes a table name, runs the generic `ReadTableRowsAsync`, and renders a paged read-only grid with "Copy row as SQL". It satisfies "you can see everything" without pretending these are world-editing surfaces — and it makes the 36-table decision visible to users.

### 4.8 A coverage manifest gate

A new TDB release adds tables. Without a gate, coverage silently rots. Generate `docs/reference/world-table-coverage.md` from code + a live DB, and add a `TcDbFact` test that fails when the live DB has a table the document does not classify. That is the difference between a one-off report and a maintained guarantee.

### 4.9 Rules that save whole editors

- **`VerifiedBuild` is never edited** (already the rule for gossip/trainer/quest links). Extend it to every new schema: leave the column out of `TableSchema` entirely so it cannot be edited or exported. This removes a column from ~25 tables at once.
- **Never edit `*_locale`** (see 4.4).
- **Never edit server-generated caches**: `creature_model_info`, `creature_movement_info`, `creature_classlevelstats`, `world_state`. Read them, mark them "computed by the server", block writes.
- **`Comment` columns are nullable** — declare `Nullable` where the DB says `YES` or the loader/export will treat NULL as `''` and guards will be wrong for the ~thousand rows that carry a comment.

## 5. Architecture / proposed approach

**Three placement rules decide where every table lives.** (a) *Contextual* — the data has an owner you can click in the world (creature, GameObject, spawn, quest, zone, instance): it is a page or card **inside that owner's window**, never a separate table screen. (b) *Workspace* — the data has its own identity but no single owner (loot tables, pools, events, conversations, item definitions): a dedicated window opened from the Content Browser or View menu, with the same draft/undo/export path. (c) *Read-only* — locales, server-computed caches, operational tables: shown where relevant and in the data inspector, never edited.

**Two new engines carry most of the work**: a `ConditionStrip` + `ConditionBuilderDialog` over the existing `ConditionCatalog`, and a generic `RowListSection` over a new `IDBSource.ReadTableRowsAsync`. Everything else is descriptors — a `TableSchema` in `Foundation/TrinityCore/TcTables.*.cs`, one `EntitySection` registered in `CreatureSectionRegistry`/`GameObjectSectionRegistry`, or one workspace window.

**New work never bypasses the existing pipeline**: reads go through `IDBSource`/`IWorldSchema`, edits are `RowEdit`s in the shared `ContentDrafts`/`InteractionDraft`, SQL comes from `SqlExport`, undo/freshness/apply/revert come free.

#### T0.1 — Write the coverage reporter

File: `Tools/world_coverage.py` (new).

```python
#!/usr/bin/env python3
"""Report which `world` tables the editor catalogues, reads or ignores.

Usage: python Tools/world_coverage.py --db-info "host;port;user;password;world" > /tmp/coverage.md
"""
import argparse, os, re, subprocess, sys

ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
CATALOG = ["Foundation/TrinityCore/TcTables.cs"] + [
    os.path.join("Foundation/TrinityCore", f)
    for f in os.listdir(os.path.join(ROOT, "Foundation/TrinityCore"))
    if f.startswith("TcTables.") and f.endswith(".cs")
]
CODE_DIRS = ["Foundation", "Scripts"]

def tables(conn):
    host, port, user, password, db = conn.split(";")
    env = dict(os.environ, MYSQL_PWD=password)
    sql = f"SELECT TABLE_NAME FROM information_schema.TABLES WHERE TABLE_SCHEMA='{db}' AND TABLE_TYPE='BASE TABLE' ORDER BY TABLE_NAME"
    out = subprocess.run(["mariadb", "-h", host, "-P", port, "-u", user, "-N", "-e", sql],
                         env=env, capture_output=True, text=True, check=True)
    return [t for t in out.stdout.split() if t]

def catalogued():
    names = set()
    for path in CATALOG:
        names |= set(re.findall(r'new\("([a-z_0-9]+)"', open(os.path.join(ROOT, path)).read()))
    return names

def mentioned():
    found = set()
    for base, _, files in os.walk(ROOT):
        if any(part in base for part in ("/bin", "/obj", "/.git", "/artifacts")):
            continue
        for f in files:
            if not f.endswith(".cs"):
                continue
            text = open(os.path.join(base, f), errors="ignore").read()
            found |= set(re.findall(r'\b([a-z][a-z_0-9]{3,})\b', text))
    return found

def main():
    p = argparse.ArgumentParser()
    p.add_argument("--db-info", required=True)
    a = p.parse_args()
    all_tables = tables(a.db_info)
    cat, code = catalogued(), mentioned()
    print(f"# World table coverage\n\nBase tables: {len(all_tables)}\n")
    print("| Table | Status |\n|---|---|")
    for t in all_tables:
        status = "editable" if t in cat else ("read-only" if t in code else "untouched")
        print(f"| `{t}` | {status} |")

if __name__ == "__main__":
    sys.exit(main())
```

#### T1.2 — Foundation row helpers

File: `Foundation/Conditions/ConditionRows.cs` (new).

```csharp
namespace ACWorldEdit.Foundation;

/// <summary>Which rows of `conditions` belong to a thing: the server's source triple.</summary>
public readonly record struct ConditionKey(int SourceType, int Group, int Entry, int Id = 0);

/// <summary>Add, edit, negate and remove `conditions` rows as draft edits.</summary>
public static class ConditionRows
{
    public static IEnumerable<Row> Select(RowSet rows, ConditionKey key, TableSchema table) =>
        rows.All(table)
            .Where(r => r.I("SourceTypeOrReferenceId") == key.SourceType
                     && r.U("SourceGroup") == (uint)key.Group
                     && r.I("SourceEntry") == key.Entry
                     && r.I("SourceId") == key.Id)
            .OrderBy(r => r.U("ElseGroup"))
            .ThenBy(r => r.U("ConditionTypeOrReference"));

    public static Row NewRow(TableSchema table, ConditionKey key, int elseGroup, int type,
        uint value1 = 0, uint value2 = 0, uint value3 = 0, bool negative = false) =>
        Row.Of(("SourceTypeOrReferenceId", key.SourceType), ("SourceGroup", key.Group),
            ("SourceEntry", key.Entry), ("SourceId", key.Id), ("ElseGroup", elseGroup),
            ("ConditionTypeOrReference", type), ("ConditionTarget", 0),
            ("ConditionValue1", value1), ("ConditionValue2", value2), ("ConditionValue3", value3),
            ("ConditionStringValue1", ""), ("NegativeCondition", negative ? 1u : 0u),
            ("ErrorType", 0u), ("ErrorTextId", 0u), ("ScriptName", ""), ("Comment", Row.NullValue));

    public static RowEdit Add(TableSchema table, Row row)
    {
        row.Validate(table);
        return InteractionEdits.Insert(table, row);
    }

    public static RowEdit Update(TableSchema table, Row before, Row after)
    {
        after.Validate(table);
        return InteractionEdits.Update(table, before, after);
    }

    public static RowEdit Remove(TableSchema table, Row row) => InteractionEdits.Delete(table, row);

    /// <summary>The next ElseGroup number (an OR-branch) in this key's rows.</summary>
    public static uint NextGroup(RowSet rows, ConditionKey key, TableSchema table) =>
        Select(rows, key, table).Select(r => r.U("ElseGroup")).DefaultIfEmpty(0).Max() + 1;
}
```

```csharp
namespace ACWorldEdit.Foundation;

/// <summary>The checks `ConditionMgr::isConditionTypeValid` / `isSourceTypeValid` make, per dialect.</summary>
public static class ConditionRules
{
    /// <summary>Why this row cannot be saved, or null when it can.</summary>
    public static string? Check(ConditionCatalog catalog, Row row)
    {
        if (catalog.Type(row.I("ConditionTypeOrReference")) is not { } type)
        {
            return $"Condition type {row.I("ConditionTypeOrReference")} is not in this server's condition types.";
        }

        if (type.Status != ConditionStatus.Usable)
        {
            return $"{type.Name} is {type.Status switch { ConditionStatus.Deprecated => "deprecated", _ => "not for this client" }}.";
        }

        var values = new[] { row.U("ConditionValue1"), row.U("ConditionValue2"), row.U("ConditionValue3") };
        for (int i = type.Params.Length; i < 3; i++)
        {
            if (values[i] != 0)
            {
                return $"{type.Name} does not use parameter {i + 1}; leave it at 0.";
            }
        }

        return null;
    }

    /// <summary>Why this source triple cannot hold conditions, or null when it can.</summary>
    public static string? CheckSource(ConditionCatalog catalog, int sourceType) =>
        catalog.Source(sourceType) is null ? $"Condition source {sourceType} is not in this server's source types."
        : catalog.Source(sourceType)!.Status != ConditionStatus.Usable ? $"{catalog.Source(sourceType)!.Name} is not usable on this server."
        : null;
}
```

```csharp
namespace ACWorldEdit;

/// <summary>
/// The conditions on one thing, as sentences: "Only if: the player is Alliance", grouped by OR-branch.

public sealed partial class ConditionStrip : VBoxContainer

    public ConditionStrip(IEntityContext ctx, ConditionKey key, Func<RowSet> rows)

    }
```

## 8. Risks, tradeoffs, open questions

**Risks**

1. **Loot key ambiguity.** TrinityCore loot tables have no unique key and 15 real duplicate rows exist. Keying on all columns makes every field edit a delete+insert; the guards still identify exactly one row, but a change to `Chance` loses the row identity in the change log (one staged change, correct result). Accept and document; alternatively add a synthetic `RowNo` (not in the DB) — rejected because exports would then be non-portable.
2. **Conditions source semantics drift.** `ConditionMgr` changes between TC versions. The catalog is generated from the server header (`Tools/generate_condition_catalog.py`); regeneration must be part of every TC bump, or the builder will offer types the server rejects.
3. **Scope explosion.** 183 tables at M each is months. The slices above are ordered by value/effort; Slice 2's engine is what keeps per-table cost near S. If the engine slips, every later slice doubles in cost.
4. **Draft size.** Loot, `creature_questitem` and `quest_poi_points` are large. Editing a *table* is fine; loading an *entry's* rows must stay bounded (the `Limit` in `RowQuery`) or the snapshot grows into tens of MB in the draft JSON.
5. **AC parity cost.** Every slice is ~1.5× if AzerothCore gets a real editor rather than "not supported". Some (cinematics, spawn groups, phases) are genuinely N/A; others (loot, quest item drops) are not, and skipping them silently breaks the "every table" promise for AC users.
6. **Hotfix writes are irreversible in a different way** (no plain SQL revert for a client patch). Slice 10 must ship the revert script *and* a warning before it is used on a live realm.
7. **Read-only tables are tempting to fake.** `creature_model_info` and `creature_movement_info` are server-computed. An editor there would produce correct-looking SQL that the server overwrites on restart.

**Tradeoffs**

- **Full coverage vs. good UX:** a generic grid on all 247 tables would technically "touch every table" and fail the brief. The three-placement-rule approach deliberately leaves 36 tables without an editor and says why in the UI.
- **All-columns loot key** trades row identity for correctness under duplicates.
- **One conditions engine** costs an up-front M but removes 7 future per-feature condition UIs.
- **Locale overlay** trades completeness (no translation authoring) for ~3.2 M rows of scope.

**Open questions (need a decision before the slice starts)**

1. **Item editing on AzerothCore:** does a new `item_template` row need a matching `Item.dbc` entry to display on a 3.3.5 client? If yes, AC item creation is "clone existing display" only. (This gates Slice 10.3; the existing gap-plan already flags it.)
2. **Hotfix writes:** is writing `hotfixes` against a live realm acceptable, or must it always be a file the operator applies? (Gates Slice 10.2's UX.)
3. **`*_locale` tables:** is displaying them enough, or does the workflow need translation authoring? (Gates T12.1's size.)
4. **`characters`/`auth`:** confirm out of scope permanently.
5. **Spawn tracking (`spawn_tracking*`, 39 k rows):** is this a world-editing feature or server tooling? It was placed in Tier 3; a "no editor" decision is defensible.
6. **`trinity_string`/`command`:** server messages and GM commands. Read-only inspector only, or should they be editable by admins? Current plan: read-only.
