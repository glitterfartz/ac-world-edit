# Status

The plan and open work for the TrinityCore database overhaul, and the project's other known gaps. Finished work is described in the architecture docs, not here. Schema differences are in `docs/DB-DIFFERENCES.md`. Target: TrinityCore `master` `world` schema (TDB 1210.26091) plus `hotfixes`; retail client 12.1.5.70575.

Phases 1–5 (interface extraction, connection and hotfixes, retail catalogs, read-only overlays and spawn moves, graveyard editing) are done. Phase 6 (creature properties) is built for TrinityCore: the template, stats, vendor, gossip, trainer and quest-link pages edit and export, with reference checks against the client and database. What remains of it is listed below as refinements, none of which blocks Phase 7. Phase 7 (quests) is built for TrinityCore: the quest editor edits and exports the five quest tables, with refinements listed below. Phase 8 (SmartAI and speech) is built for TrinityCore: the shared behavior panel edits a creature's `smart_scripts` rules, timed action lists, AIName and `creature_text` lines and exports them, with refinements listed below. Phase 9 (waypoints) is built for TrinityCore: the waypoint layer reads `waypoint_path` and `waypoint_path_node`, and a node's position, facing and delay edit and export, with refinements listed below. All nine phases are built, and the behavior panel also edits TrinityCore AreaTrigger rules: client triggers (source type 2) and server-spawned triggers' templates (types 11 and 12), with refinements listed below.

**Next: editor gap plan.** Phases 10 onward (spawn authoring, conditions, GameObjects, loot, movement, pools, events, creature pages, quest map data, travel, ambience, cinematics, text and items) are planned in [`gap-plan.md`](gap-plan.md); each phase lands as its own rows in this file when it starts.

## Decisions and design

- The dialect follows the client kind: Wrath335 uses AzerothCore and Retail uses TrinityCore. There is no autodetect, so a schema mismatch fails with a dialect-specific error.
- **Drafts are per client profile** (`user://drafts/wrath/`, `user://drafts/retail/`), so an AzerothCore viewer and a TrinityCore viewer run side by side without sharing a draft lock. Switching client in-app reopens the other profile's drafts instead of discarding them.
- Hotfixes are read from a second database name on the same connection (default `hotfixes`), falling back to client DB2.
- Each phase delivers full read and edit/export parity for its area, with its own commit(s), tests, and a visual check where the UI changes.
- **An export source with no SourceDialects entry is AzerothCore.** The source key is a one-way hash of the connection, and every draft saved before TrinityCore support was made against AzerothCore, so there is nothing to migrate; SourceDialects.DialectOf defaults to AzerothCore.
- **Dialect-native rows.** Read-only overlay results are shared records translated by each dialect. Editing stays on the generic path, `RowEdit(Table, Key, Before, After)` → `SqlExport`, with each dialect's own table catalog, so structural differences (`quest_objectives` 1:N rows, `creature_template_difficulty`, `creature_template_gossip`) round-trip without a lossy neutral model. Editors switch descriptors (field groups, enums, catalogs), not data models.
- **`IWorldSchema` grows per phase.** It has `Tables` and `Sql`, plus the creature descriptors. `Smart` is the dialect's `SmartCatalog`; the quest pages are drawn by `AcQuestPanel` / `TcQuestPanel` over `AcTables` / `TcTables` instead of a schema descriptor. AzerothCore's static data is `Ac`-prefixed (`AcTables`, `AcQuestModel`, `AcNpcFlags`) and used by AzerothCore code only; the quest types and placeholders both pages show are in `QuestVocabulary`.
- **Creature pages are descriptors, not per-dialect classes.** A page is an ordered list of groups; a group is fields bound to one row or an item list (source table, parent filter column, per-item fields, nested lists, add/remove). Each dialect fills the descriptor in; one renderer draws it. Dialect-specific section adapters use `Ac` / `Tc` prefixes in `AzerothCore/` / `TrinityCore/` directories.
- **Editors read the dialect only through `IDBSource.Schema`:** `CreatureSectionRegistry` filters sections by schema support (Quests is one `QuestsSection` for both dialects); `QuestPanel` is shared and `AcQuestPanel` / `TcQuestPanel` draw the pages that differ (TC replaces `RequiredNpcOrGo`/`RequiredItem` with an Objectives list); `BehaviorPanel` (and its creature `BehaviorSection` / `SpeechSection`) is shared and takes `SmartCatalog` from the open connection's dialect.

Verification per phase: the default suite; Db tests with `ACWORLD_DB_INFO` (AC regression) and `ACWORLD_TC_DB_INFO` (TC); the retail corpus with `--settings corpus.runsettings` and `ACWORLD_RETAIL_DIR`. Visually: `--client-shot-overlays` (retail, Goldshire); open the creature, quest and behavior editors in both modes and confirm they show the dialect's fields; export SQL from the pending changes window and run it against a scratch copy of `world`.

Status values: **partial**, **not started**, **deviates** (built differently from the plan).
